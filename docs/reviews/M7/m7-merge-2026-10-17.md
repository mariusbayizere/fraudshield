**Verdict: CHANGES_REQUIRED**

The three commits are sound on their own terms: every conflict resolution in `8c8cf48` keeps both
sides with nothing dropped, V70 now closes all five SECURITY DEFINER functions to PUBLIC and pins
their `search_path`, and the gitleaks test change is deterministic. The verdict comes from the
integration itself. With M6 on the branch, M6 and M7 each expect the other to do the wiring. M6's
ports are implemented only by test doubles. M6's audit events never reach the hash chain. M7's API
is still test-only. That leaves two MAJOR findings, and both can be closed by an owner decision
recorded with an acceptance criterion; neither needs a large code change before the merge.

## V70 after `3c13c5c`

- **PUBLIC is closed on all five functions.** `auth_employee_id_registered(text)`,
  `auth_find_user_institution(uuid)`, `audit_chain_head(smallint)`,
  `audit_chain_hashes(smallint, bigint, bigint)` and
  `audit_chain_last_seq_before(smallint, timestamptz)` are all revoked from PUBLIC before the
  grants, and the signatures match the definitions exactly.
- **Grants are as intended.**
  - `auth_*` → `fs_app`.
  - `audit_chain_head`/`audit_chain_hashes` → `fs_app` (anchoring) and `fs_compliance_ro`
    (verification).
  - `audit_chain_last_seq_before` → `fs_compliance_ro` only, which matches `AuditChainVerifier`
    ("runs as `fs_compliance_ro`").
  - The revoke removed no path that real code relied on: the anchoring job calls only
    `audit_chain_head`/`hashes`, both still granted to `fs_app`.
- **`search_path`.** All five set `SET search_path = fraudshield, pg_temp` and schema-qualify
  every table, so the classic SECURITY DEFINER hijack via a caller-controlled schema or `pg_temp`
  object is closed.
- **Owner rights.** The owner is `fs_migrator`, with NOBYPASSRLS and no `FORCE ROW LEVEL SECURITY`.
  As table owner it is exempt from RLS, which is what lets the functions answer across tenants.
  They return positions, hashes, a boolean or an institution id, never content, as documented.
- **Other V70 objects.**
  - `users.version`: a new column falls under existing table-level grants, so `fs_app` gets it,
    and V70 grants `fs_app_readonly` column SELECT explicitly.
  - `fs_compliance_ro` still has no SELECT on `users` (asserted at
    `DatabaseSecurityTest.java:398-401`), and `fs_scorer` gets nothing (asserted by the
    role_table_grants check).
  - The index carries no privileges.
  - V70 creates no tables, views or sequences, so nothing else can leak to roles M6 added later.
- **Editing in place.** This is acceptable. V70 is absent from `origin/main` (verified), the merge
  base with main is `b77008e`, so `fs-migration-guard` sees V70 as new, and V70 sorts above M6's
  V60–V67. CI databases are ephemeral. Persistent developer databases are covered in finding 7.
- **Root-cause statement and test coverage.** See findings 3 and 4.

## Integration of the M6 and M7 backends

- **Hybrid persistence rule.** M6 follows it by inspection:
  - JPA for configuration: `ThresholdRepository`, `RuleRepository`, `BreakerSettingsRepository`,
    `BatchJobEntity`.
  - Explicit SQL for the hot path, hypertables and append-only tables (`JdbcDecisionStates`, the
    spool's `PostgresSink`, `JdbcIdempotency`).
  - No `@EnableJpaRepositories`. The application class in the root package supplies the
    auto-configuration package (`DecisionWiring.java:86-89`), and M7 uses
    `@AutoConfigurationPackage` (`AuthPersistenceAutoConfiguration.java:18`).
  - M6 has its own `PersistenceSettingsGuard` and its own `TenantTransactions`
    (`decision/adapter/jpa`). It is the same design as `audit.jdbc.TenantTransactions` but a
    duplicate class.
- **Transaction managers.** Only one exists. No module declares a transaction manager bean; the one
  hit for `TransactionManager` in `AuditVerifyCommand` is the CLI's own context. M6's
  `TenantTransactions` takes Boot's `PlatformTransactionManager`, which is a
  `JpaTransactionManager` because `spring-boot-starter-data-jpa` is on the classpath. No test of
  the assembled application proves this (finding 7).
- **Audit.** M6 does not write through `AuditLog`; it publishes to Kafka with nobody consuming
  (finding 2).
- **M7's API surface** is not assembled into M6's application and is still test-only. The two
  milestones' handover notes point at each other (finding 1).

## The test change

- `GOOD` is fixed. Digits separate every letter, its entropy is well above the generic rule's
  threshold, and `GOOD = "…"` is not a key-like assignment, so the repository scan does not flag
  it. The CI secrets job is green.
- For a pinned binary and config the scanner is deterministic, so `GOOD` is either always detected
  or always not. CI shows it is detected.
- The control test and the regeneration test are deterministic and pass the deletion standard.
- The many-values test is now a convergence check, not a proof of regeneration (finding 9).
- The tests run in CI, not skipped: `tools/bin/gitleaks` is the committed launcher, and the python
  job runs `pytest` in `tools`.
