Once the fallback is configured, the store asks PostgreSQL synchronously on every Redis miss, which includes every first transaction of a new account and every new device, not only expired accounts. Requests for accounts whose Redis state is intact then queue as well, pass the API's per-call deadline, and the API's breaker moves **all** traffic to `fallback-rules-2`. | D2 | MAJOR | `notify/.../vault/KmsKeyProvider.java:67` and `PassphraseKeyProvider.java:92` (`permanent("no master key with id …")`); `EnvelopeConsumer.java:200-204`; ADR 0069 (rotation paragraph, around line 104) | **A normal key rotation now loses customer block SMS.** "Unknown key id" is dead-lettered as permanent. During a rolling rotation, instances already switched to the new `current-key-id` write contacts under it (M7's onboarding or re-enrolment). A notify consumer on an instance not yet reconfigured reads such a row, gets "no master key with id k2", and dead-letters the SMS. Before the fix the SMS was retried until the instance was replaced and then sent. Nothing re-drives `<topic>.dlq` (no consumer exists for it), so the customer is never told of the block. ADR 0069 says old ids must stay configured, but it does not require a new id to be made readable everywhere **before** it becomes current.
