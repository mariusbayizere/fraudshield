\section{Introduction}
\label{sec:introduction}

Digital payments in East Africa include mobile money: person-to-person transfers, cash-in and
cash-out through agents, merchant payments, and USSD sessions on basic handsets. Cards and bank
transfers run alongside them. Dal Pozzolo et al.'s practitioner account of fraud detection is drawn
from card transactions \cite{dalpozzolo2014lessons}. The fraud documented on mobile channels includes
SIM-swap takeover \cite{lee2020simswap} (studied on US carriers), attacks through add-on SIM hardware
\cite{phipps2018thinsim}, and scams carried out by SMS and phone call
\cite{razaq2021scams,dogan2025grift}. USSD, moreover, carries no device fingerprint (resolution D-04).
We do not repeat the frequently quoted figures about the growth of mobile money fraud in the region: the
claims register of this project lists each of them as unverified or replaced, and this paper states
none of them as fact (Section~\ref{sec:limitations}).

FraudShield is a fraud detection system built to a written specification (a software requirements
specification, SRS, corrected by a register of \nResolutions{} binding resolutions; the identifiers
this paper uses are listed in Appendix~\ref{app:identifiers}): a synchronous decision path that
returns a decision to core banking with a server-side latency target, an explainable scoring model,
and an analyst console (the console is not part of this paper's release). Building it required data on
which the model could be trained and evaluated. The build specification required an agent-based,
seeded simulator for it, and we built one without first searching for existing
datasets. A search recorded afterwards found that public, labelled East African fraud
datasets already existed: a real one from a payments company in Uganda and a synthetic mobile-money
one from Makerere University (Section~\ref{sec:related}; claims register, C-8). Ours is not the first.
It is FraudShield-EAC, an agent-based, seeded simulator of customers, agents, merchants and
\nScenarios{} fraud scenarios across Rwanda, Kenya, Tanzania, Uganda and the Democratic Republic of
the Congo.

A synthetic benchmark invites a particular failure. It is easy to generate one on which a model
scores highly and hard to know whether the score measures learning or the generator. Much of this
project's effort went into interrogating the benchmark until it gave up its structure, and
publishing each interrogation whether or not it flattered the dataset. That record, not the
benchmark, is the first contribution.

\paragraph{Contributions.} We claim the following, each of which a reader can check against the
repository and disagree with:
\begin{enumerate}
  \item \textbf{A record of benchmark audits and their measured failure modes}
        (Sections~\ref{sec:dataset}, \ref{sec:evaluation} and \ref{sec:discussion}). The strongest
        single engineered feature reaches \nGateFloor{} on the evaluation test rows, so a model AUC
        quoted against chance overstates the quantity that matters; on a diagnostic
        model, \nGroupsAboveCeiling{} disjoint feature groups each exceed the \nCeiling{}
        single-feature ceiling alone; and the controls
        that failed, how each failure was found, and which of the resulting rules a check now
        enforces and which remain written rules.
  \item \textbf{A detection failure on a non-burst variant pre-specified in repository history}
        (\prespec{656d24e}{2026-09-22}{6bc842d}{2026-09-22}; Section~\ref{sec:generalisation}): recall \nRevRecall{} \nRevCI{} against
        \nBaseVarRecall{} \nBaseVarCI{}, measured on a held-out shape. Its cause is inferred, not
        isolated: the variant differs from the base scenarios in more than one respect.
  \item \textbf{Generalisation nulls} (Section~\ref{sec:generalisation}): leave-one-country-out
        and a novel variant held out in time both fail to test generalisation on this benchmark. A test
        checks that no fraud parameter is keyed by country, and we infer that the country null
        follows from that and the variant null from the variant's multi-row shape; no experiment
        isolates either cause. The verification milestone (M10) would repeat both at the
        specification's \nSpecRows{}-row scale; it changes no fraud parameter, so it could show
        whether the nulls hold at scale but could not make leave-one-country-out informative.
  \item \textbf{The latency--explainability frontier} (Section~\ref{sec:evaluation}): how the
        median cost of an exact TreeSHAP explanation changes across tree complexity on one
        development laptop, reported at the median only, because the measured \nPctlTail{}th
        percentile was not credible: in \nFrontNegative{} configurations it showed a negative
        explanation cost. It is a measurement of one model on one machine. M10 would add the
        frontier the specification defines: the single-request \nPctlTail{}th percentile of the
        ensemble with exact TreeSHAP, in the multi-process scoring service, on dedicated hardware,
        and whether the \nLatencyPNineNineShap{}~ms constraint binds; it would not test our
        inference that the cost does not depend on the data, which needs another benchmark.
\end{enumerate}
The redundancy finding of the first contribution is stated separately in Section~\ref{sec:evaluation} because it is
a result about how this generator encodes signal, not a detail of one table.

The system itself, \nFeatures{} features computed on batch and online paths that do not import each other, with a parity suite and
a published temporal split, is the setting of these results and is not claimed as a research
contribution. Its deviations from the specification are recorded as architecture decision records
(ADRs), which we cite where they matter.
