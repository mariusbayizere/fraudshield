# M7 walkthrough — staff identity, authorisation, administration and audit

## What was built

M7 adds three backend modules:

- `backend/audit`: the hash-chained audit writer, tenant transactions, signed daily anchors and
  `fraudshield audit verify`.
- `backend/auth`: staff sign-in and sessions, Google sign-in, registration, password reset, API
  keys, and the security chain that authorises every request from the contract.
- `backend/admin`: accounts, approvals, the office IP allowlist, API keys and audit search.

They are Spring Boot auto-configured libraries. The M6 application picks them up by depending on
`fraudshield-admin`.

## The decisions to be able to defend (ADR 0014, ADR 0070)

1. **Authorisation comes from the contract, deny by default.** The golden matrix
   (`contracts/openapi/authorisation-matrix.yaml`) is packaged into the jar and read at startup
   (`ContractPolicy`). A request that matches no contract operation is refused. So an ingest or
   alert endpoint that M6 has not written yet already refuses the wrong callers.
   `AuthorisationMatrixTest` proves it over HTTP: 84 operations × 9 callers (anonymous, four
   roles, four API-key scope sets).
2. **Stateless JWTs that can still be revoked within seconds (D-27).**
   - Every token carries `token_version` and `sid`.
   - `SessionStateCache` checks both on each request: 1 s in process, 2 s in Redis, the database
     behind them.
   - Changes are announced on Redis pub/sub after commit.
   - The measured cross-instance delay is tens of milliseconds, and about 2.3 s when the
     announcement is lost (see `docs/benchmarks/`).
3. **Refresh tokens rotate, and reuse kills the family.** Presenting a rotated token again means it
   was copied, so every token of that sign-in is revoked. The family keeps its first token's
   expiry, so a sign-in lasts at most 7 days.
4. **The lockout cannot be used to find accounts (D-26).**
   - Unknown emails and inactive accounts get the same 401-then-423 sequence as real ones.
   - Every path spends one bcrypt.
   - Office addresses on the allowlist get a higher per-IP ceiling. A per-(IP, email) limit still
     stops one person from exhausting it.
5. **API keys use HMAC with a pepper, not bcrypt (D-19).** bcrypt's 100-300 ms per check would be a
   denial of service at 10,000 TPS. Keys are cached for 2 s and revoked through pub/sub, and the
   measured revocation is under 100 ms.
6. **Audit tamper evidence (D-32).**
   - The database assigns each row's chain position and hash (V8).
   - The anchoring job signs a Merkle root (RFC 6962) over each partition's new rows daily, with
     Ed25519.
   - `fraudshield audit verify` checks signatures, recomputes the roots and re-hashes the chain.
   - A superuser who rewrites a row and its hash consistently is still caught by the signed anchor
     (`AuditAnchoringTest`).

## How to run and demonstrate

- Build and test: `cd backend && ./mvnw verify`. Database and Redis tests need Docker, or
  `FRAUDSHIELD_TEST_POSTGRES_URL` (a TimescaleDB 2.30 server with a superuser) and
  `FRAUDSHIELD_TEST_REDIS_URL`.
- Watch a lock: sign in five times with a wrong password; the fifth answers 423, and the recording
  mailer (tests) or Mailpit (Compose) receives the unlock link.
- Tamper and detect:
  1. `fraudshield audit verify --from … --to …` reports VERIFIED.
  2. As a superuser, update one `audit_events` row with `session_replication_role = replica`.
  3. Run `fraudshield audit verify` again: it prints the partition and sequence number of the
     change.

## What the numbers mean

- The invalidation and revocation timings were measured on the author's laptop (4 cores,
  7.6 GiB), between two in-process instances that share only Redis and the database. They show
  the mechanism works well inside the 5 s bound. They are not a claim about a loaded production
  cluster.
- The bcrypt timing (> 100 ms per hash at cost 12) is deliberately slow. It is why API keys do not
  use bcrypt.
