# M3 walkthrough — the feature pipeline

Every claim below is followed by what backs it: a test, a measurement with its commit, or a
statement that nothing does. That last case is not rare and is the point of writing it this way.

## What was built

**All 44 features of Part E.2, on two independent paths.** `fraudshield_ml.features.batch` reads
whole histories and filters; `fraudshield_ml.features.online` accumulates from arrivals. Neither
imports the other — `test_the_two_paths_do_not_import_each_other` walks the import graph — and both
import only the declarative registry, the pure data records and three enumerated primitives.

*Backed by:* `test_completeness.py` asserts the registry's 44 and the implemented set are the same
set. 266 tests pass; 30 of them are the parity, mutation and independence suites.

**A declarative registry that refuses an underspecified feature.** Eleven contract fields, none
with a safe default: `self_inclusion`, `nesting`, `smoothing`, `history_basis`,
`history_requirement`, `fallback_behaviour`, `label_basis`, `minimum_history`, `history_key`,
`reference_data_basis`, and `computable`. Six of the first ten arrived by attacking the schema with
the most differently-shaped feature available rather than by designing it.

*Backed by:* `test_registry.py` — each field has a refusal test and a control proving the refusal is
not unconditional.

**A parity suite with an executed mutation table.** Prefix replay, the cold-cache case, the
configuration-change fixture property. Twelve of thirteen mutation rows executed; row 9 is pending
because the DB fallback path does not exist (PB-36).

*Backed by:* `docs/ml/training_serving_parity.md` carries the table with each row's result and date.

**A dataset fingerprint (PB-41)** over output rows, and an export that refuses to bundle a realism
report describing other data.

*Backed by:* `dataset/tests/test_fingerprint.py`, `test_export.py`; the full dataset suite passes,
126 tests.

**A computability check (PB-44, PB-47).** Every feature declares whether the benchmark can feed it;
`fs-features computability` computes all 44 over a generated dataset and fails when a declaration
disagrees with the data, in any of six directions.

*Backed by:* `docs/benchmarks/m3_computability_fad43dd.txt` — 44 features over 10,000 scored rows
from a 200,000-row corpus, exit 0.

## What the measurements say

**Thirty-eight of the 44 can be fed by this benchmark; six cannot, and two more carry no
variation.** The six read reference data that neither the dataset nor M1's schema holds. Two —
`just_below_limit_flag` and `accounts_per_device_7d` — are present, complete and constant.

*Backed by:* the computability artefact above. **Not backed by reasoning:** an earlier estimate in
this repository said eight, by reading each feature's inputs. The measurement said six, and
disagreed in both directions.

**The benchmark is velocity-separable.** One feature, `velocity_ratio_1h_vs_30d`, reaches
`max(AUC, 1−AUC)` of **0.894 ±0.032**; four more exceed the D-08 ceiling of 0.80.

*Backed by:* `docs/benchmarks/m3_single_feature_auc_fad43dd.txt` — corpus 200,000, 20,000 scored,
166 confirmed fraud, folds grouped by whole accounts, commit `fad43dd`. The full statement is
`docs/benchmarks/single_feature_baseline.md`.

**The D-08 claim as previously quoted is refuted.** "No single feature separates the classes beyond
AUC 0.80" was measured on the dataset's *columns* and quoted as a property of the features a model
is given.

*Backed by:* claims register C-9 (refuted as stated) and C-14 (the measurement).

**Simultaneous transactions do not occur on this benchmark.** Zero of 201,243 rows share an
`(account_id, transaction_timestamp)` pair, so the strictly-earlier predecessor rule costs nothing
here. `tx_count_60s` is non-zero for about 0.13% of rows.

*Backed by:* the measurement recorded in `registry.SIMULTANEOUS_PREDECESSOR_NOTE` and the datasheet,
at tree `65c8351`.

**Component folding is unavailable for three of four relational keys.** Counterparty and geo-cell
graphs are single components spanning 100% of accounts; agent reaches 38%.

*Backed by:* `docs/research/component_sizes.json` at tree `d85385f`.

## What is claimed and not backed

- **That the features are correct in the sense of matching Part E.2's intent.** Hand-computed unit
  tests back each feature's arithmetic, and parity backs the two paths agreeing. Neither is
  evidence that the specification was read correctly, and six definitions contained forks the
  registry had to settle.
- **That the parity suite would catch a defect both paths share.** It cannot, by construction. The
  `velocity_ratio_1h_vs_30d` account-filter defect lived in exactly that gap and was found by an
  index-equivalence test, not by parity.
- **That the 0.894 figure transfers to any other scale.** Single-feature AUC on this benchmark
  moves with dataset size by more than seed noise, unexplained since M2 (E2).
- **That `corridor_class` works for the two classes this dataset cannot produce.** They are
  unit-tested against an invented pack and unexercised by any row.

## Try it

```bash
uv run fs-dataset generate --output /tmp/bench --seed 20260917 --rows 1000000
uv run fs-dataset packs --output /tmp/packs.json
uv run fs-features computability /tmp/bench --packs /tmp/packs.json \
    --corpus-rows 200000 --sample-rows 10000
uv run fs-features auc /tmp/bench --packs /tmp/packs.json \
    --corpus-rows 200000 --sample-rows 20000
```

The generation takes about thirty-five minutes and the two checks about ten and twenty. `auc` exits
**1**, and is expected to: five features exceed the ceiling.
