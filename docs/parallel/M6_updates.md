## Contracts M5 and M7 must honour

- **M7 implements `ApiKeyAuthenticator`** (`backend/ingest/.../ingest/auth/ApiKeyAuthenticator.java`):
  `Optional<ApiPrincipal> authenticate(String rawKey)` where `ApiPrincipal(apiKeyId,
  institutionId, Set<ApiScope>)` and `apiKeyId` is the `api_keys.id` row (batch jobs reference it).
  The API refuses to start without a bean. Keys are checked on `/api/v1/transactions/**`,
  `/api/v1/decisions/**` and `/api/v1/jobs/**` only; staff-path security (403 for API keys on
  `/alerts`, `/admin`) is M7's, and `IngestApiTest` only asserts that a key gets no 2xx there.
- **M7 implements `WebhookEndpoints`** (`notify/.../webhook/WebhookEndpoints.java`): the URL and
  every active signing secret (two during rotation) per institution. Without it webhooks do not
  start and states remain on `fs.decisions.final` and `GET /decisions`.
- **M7's staff API calls** `DecisionTransitionService.analystDecidesHold` (it cancels the hold
  atomically against the timeout poller; refusal `REVIEW_DEADLINE_PASSED` maps to 409
  `review-deadline-passed`) and `CircuitBreakerPort.countConfirmedFraud` (the D-18 numerator's
  analyst-confirmed half). Senior overrides are not implemented in M6.
- **M5 (scorer), ADR 0033 as applied**: the API sends `ScoreRequest` without `context`
  (transaction, configured limits, traceparent); the Java side builds no `AccountContext` and
  computes no feature (ADR 0061 point 7). It reads `feature_store_degraded` (19) into the
  `fs_feature_store_degraded_total` metric and persists it with `account_context` (18) on
  `fraud_scores` (V66). Because Java no longer computes features, **there is no Java/Python
  parity gap to close**; the earlier "no cross-language parity test" item is withdrawn.
- **M5 (scorer), the database fallback** (PB-69): `PostgresFallback` on
  `m6/featurestore-fallback` reads as `fs_scorer` and raises `FallbackUnavailableError` rather than
  answering "never seen" when the database cannot answer. `FeatureStore.read` does not catch it, so
  the scorer's serving layer must map it to `UNAVAILABLE` (the API then decides on
  `fallback-rules-2`). M5 should confirm that mapping in its serving code; M6 did not edit it.
- **Contract gap, closed:** `notification-customer.parameters.masked_account` is filled from the
  vault's masked account number (ADR 0069 point 8); the contract is unchanged.
- **M7's onboarding enrols customers** by calling `AccountTokens.tokenise` (account number to
  token) and `VaultContacts.store` (contact details under that token). Both are Spring beans when
  `fraudshield.vault.url` is set; neither has an HTTP endpoint in M6.
- **M9 binds a `KmsClient`** for its key service and runs `KmsClientContract` (notify's test jar)
  against it. Production uses `fraudshield.vault.key-provider=kms` (the default); `configured` keys
  are refused outside `dev`, `demo` and `test` profiles (ADR 0069 point 10).

### The first measurement (2026-09-22, Codespace)

`docs/benchmarks/2026-09-22-M6-decision-latency.json`, produced by
`DecisionLatencyBenchmark` (opt-in: `-Dfs.benchmark=true -Dfs.benchmark.rates=… -Dfs.benchmark.seconds=30`).
Open-loop load against the real API with PostgreSQL, Redis and Kafka in Testcontainers and a gRPC
scorer double that answers at once, so **model inference (M5) is not in these numbers**.

container was restarting every few seconds and the one-minute load average at the end of the run

- **Gate (end-to-end p95 < 50 ms at the largest achievable load): not met.** Met at 50 req/s
  (42 ms); 69–109 ms at 100–200 req/s, where the load generator, API and all three stores share
  four oversubscribed cores. 25 req/s at 53 ms against 42 ms at 50 req/s is the noise level of this host.
- Server stage p50 / p95 over all runs (ms): idempotency claim 6.6 / 285, account read 7.9 / 58.7,
  score 5.2 / 21.0, fast state writes 4.5 / 41.9, spool 2.2 / 8.9, idempotency complete 5.2 / 44.0,
  decide 0.02 / 0.5. C.2 budgets single Redis round trips at 1–2 ms p95; here one `EVAL` takes
  ~6 ms at the median, which points at CPU starvation of the Redis container rather than at the
  number of round trips. The single-command stages are the first thing to re-measure on a quiet host.
- Two fixes came out of the measurement: the feature-store update and MCC counting now run after
  the response (as C.2 lists them), and counterparty/device distinct counts are computed in Redis
  instead of shipping one member per payment to Java (ADR 0061 point 7). Together they took the
  server decision p95 at 100 req/s from 124 ms to 32 ms on the same host.
- Proposed status for the gate evidence: **NOT MET**, with the result above (Principal Review
  finding 15). The reviewer could not reproduce the one passing figure — their 50 req/s run
  measured client p95 325 ms at load average 25 — so VERIFIED_AT_REDUCED_SCALE must not rest on
  it, and `m6-complete` must not be tagged. **The benchmark was not re-run after the review**: the
  host has not been quieter, and the changes since (idempotency verification, the dead-letter
  path, the rate limiter, JPA for configuration) are not on the synchronous decision path except
  for the limiter's single Redis round trip. A measurement on a host that can support it is the
  open work, and it is owed before the tag.

## The owner's persistence rule, adopted (ADR 0068, following M7's ADR 0071)

- **JPA with Hibernate**: the risk configuration (`JpaConfiguration` replaces `JdbcConfiguration`),
  batch jobs, and the demo seeder's institution, users and risk configuration.
- **Explicit SQL**: the synchronous decision path, every append-only table, the hypertables, the
  audit chain, the PII vault, and the PostgreSQL features JPA has no expression for.
- Every configuration table except `alert_rules` is append-only, so those entities are
  `@Immutable`: a new configuration is a new version.
- `ddl-auto=validate` and `open-in-view=false`, enforced by `PersistenceSettingsGuard`; row-level
  security applies to Hibernate through `TenantTransactions`; one configuration load is three
  statements whatever the number of rules, asserted with Hibernate statistics.
- **For the merge**: the entities are per module, because putting them in `backend/persistence`
  puts that module and its synthetic-data start-up guard on the API's classpath, which stopped
  every API test. M7's entities live in its own module too, so the shapes agree.

## Newly built in M6 after the review

- **The PII vault (D-20, ADR 0069)**: a separate instance, its own roles, AES-256-GCM envelope
  encryption with a per-row data key, a `KeyProvider` interface with a configuration-backed
  implementation (the KMS port and its contract suite were added on 2026-09-23; the vendor binding is M9's). It closes ADR 0065's `masked_account` contract gap. Its code was
  committed inside `452d1d9`, whose message describes only the JPA change — the two were staged
  together by mistake, and the history is not rewritten because the branch is pushed.
- **Rate limiting (E.1)**: a token bucket per API key in Redis, 429 with `Retry-After`, and a
  per-instance bucket when Redis is unavailable, marked `RateLimit-Degraded: true` and counted, so
